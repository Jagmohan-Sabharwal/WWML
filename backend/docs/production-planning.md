# Production planning and asset locks

The production plan is a relational hierarchy:

```text
Production
  Sequence (ordered within the production)
    Scene (ordered within the sequence)
      Shot (ordered within the scene)
        Required Asset (an ordered editorial need)
          Locked Asset (zero or one selected registry file)
```

A shot can require multiple assets. Each requirement is one slot with a name,
description and media type. Add multiple slots when a shot needs multiple files.
An unfilled requirement has no locked_assets row. A lock references an existing
Asset Registry record; the same asset can satisfy multiple requirements, shots or
productions. No media is copied, uploaded or generated by this feature.

## API

All paths below have the `/api/v1` prefix. Swagger is available at `/docs`.

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/productions` | Create a production |
| GET | `/productions` | Existing paginated production list |
| GET | `/productions/{production_id}` | Read a production |
| POST, GET | `/productions/{production_id}/sequences` | Create or list sequences |
| POST, GET | `/sequences/{sequence_id}/scenes` | Create or list scenes |
| POST, GET | `/scenes/{scene_id}/shots` | Create or list shots |
| POST, GET | `/shots/{shot_id}/required-assets` | Create or list requirements |
| PUT, GET, DELETE | `/required-assets/{requirement_id}/locked-asset` | Lock, read or explicitly unlock a selection |

Create a production with `{"name":"Ocean documentary","description":null}`.
Optional status uses the existing draft/in_production/completed/archived values.
Create each child with `{"name":"Opening","position":1,"description":null}`.
Requirements additionally need `"media_type":"video"` (or audio/image/document/other).
Use each response's UUID in the next child endpoint. Parent IDs come from the path;
clients cannot override them in the request body.

Positions are positive integers, unique among siblings, and may contain gaps.
Child lists sort by position then UUID and accept `page` (default 1, maximum
1,000,000) and `page_size` (default 20, maximum 100). Responses use the existing
`items`, `total`, `page`, `page_size`, `total_pages` envelope. A nonexistent parent
returns 404, while an existing parent with no children returns an empty page.
Cross-production children never appear in another parent's list.

Malformed input returns 422. Duplicate sibling positions return 409 with
`detail.code=position_conflict`. POST returns 201. Planning nodes currently support
creation and reading; moving, editing and deletion workflows are not part of this
release. Production status does not yet enforce a workflow state machine.

## Lock semantics

PUT `{"asset_id":"<registry-asset-uuid>"}` to the requirement's locked-asset endpoint.
The first selection must reference an active registry asset with the required media
type. Missing/deleted assets return 404; incompatible media returns 409 with
`media_type_mismatch`. The response contains `required_asset_id`, `asset_id`,
`checksum`, `storage_uri`, and `locked_at`.

The selection stores the checksum and storage URI at lock time. Subsequent registry
metadata edits or soft deletion do not rewrite that snapshot. This is a recorded
file selection, not a storage-level retention lock: use immutable/versioned storage
URIs and verify checksums before consuming bytes. The API does not prevent an
external storage system from replacing or removing a file.

Repeating PUT with the same asset returns the original snapshot (including after
registry soft deletion), without changing its timestamp. A different asset returns
409 `already_locked`; explicitly DELETE the selection before choosing another.
DELETE returns 204, including when an existing requirement is already unlocked.
It removes only the selection, preserving the requirement and canonical asset.
GET returns 404 if the requirement has no selection. Unlocking does not retain an
audit history in this release.

Row locks serialize competing choices and unlocks on the requirement. Initial
selection also locks the registry row while checking its active state and copying
the snapshot. The database primary key permits at most one lock per requirement.
Foreign keys restrict hard deletion of referenced parents and registry assets.

## Migration and verification

Run `alembic upgrade head` before starting the API; Compose does this automatically.
Migration `0008_production_structure` follows `0007_productions` and adds
`production_sequences`, `scenes`, `shots`, `required_assets`, and `locked_assets`.
Downgrading to 0007 removes planning records and selections but preserves productions
and registry assets. Existing read APIs and frontend behavior remain compatible.

Unit tests cover request validation and lock invariants. PostgreSQL integration
tests cover full traversal, parent isolation, pagination, duplicate positions,
reuse, snapshot retention, competing selections, foreign keys, and migration
upgrade/downgrade consistency. No AQR, AI or Google Drive behavior is added.
